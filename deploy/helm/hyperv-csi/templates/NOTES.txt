What works right now: CreateVolume, DeleteVolume, ControllerPublishVolume,
ControllerUnpublishVolume, and NodeStageVolume/NodeUnstageVolume. A PVC will
provision, bind, and attach to its node VM, and the node plugin will format
and mount it at the staging path; a pod that tries to actually use it will
still fail, since NodePublishVolume — the bind-mount into the pod's path — is
not implemented.

Watch a volume get provisioned:

  kubectl apply -f - <<'YAML'
  apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: hyperv-csi-smoke
  spec:
    accessModes: [ReadWriteOnce]
    storageClassName: {{ .Values.storageClass.name }}
    resources:
      requests:
        storage: 1Gi
  YAML

  kubectl get pvc hyperv-csi-smoke -w

Bound means the agent created a VHDX under its configured CsvVolumesRoot; the
file is named after the PVC's volume handle. If it stays Pending, the reason is
in the provisioner's events and the driver's logs:

  kubectl describe pvc hyperv-csi-smoke
  kubectl logs -n {{ .Release.Namespace }} deploy/{{ include "hyperv-csi.fullname" . }}-controller -c hyperv-csi-driver
  kubectl logs -n {{ .Release.Namespace }} deploy/{{ include "hyperv-csi.fullname" . }}-controller -c csi-provisioner

A TLS error in the driver's logs with nothing on the agent side usually means
the client certificate's fingerprint isn't in the agent's config — the agent
rejects unrecognized callers during the handshake and logs the fingerprint it
was shown.
{{ if eq .Values.storageClass.reclaimPolicy "Retain" }}
Note: the StorageClass reclaims with Retain, so deleting the PVC leaves the PV
and the VHDX behind, to be removed by hand. DeleteVolume is implemented — set
storageClass.reclaimPolicy=Delete once you have seen it succeed against your
own hosts.
{{- end }}
