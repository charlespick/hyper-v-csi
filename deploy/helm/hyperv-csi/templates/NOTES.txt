What works right now: the whole path from PVC to running pod. CreateVolume and
DeleteVolume, ControllerPublishVolume/ControllerUnpublishVolume,
NodeStageVolume/NodeUnstageVolume, NodePublishVolume/NodeUnpublishVolume,
online expansion through ControllerExpandVolume/NodeExpandVolume,
NodeGetVolumeStats, and ValidateVolumeCapabilities. A PVC will provision, bind,
attach to its node VM, get formatted and mounted, and serve a pod that uses it.

Snapshots are built — CreateSnapshot, DeleteSnapshot, ListSnapshots, and
restoring a volume from a snapshot through CreateVolume's VolumeContentSource
— but external-snapshotter is only deployed when
controller.snapshotter.enabled is set, and none of this, restore included,
has been exercised against a real Hyper-V cluster. Restoring from another
volume (cloning a PVC) is not implemented and is not advertised.

Watch a volume get provisioned:

  kubectl apply -f - <<'YAML'
  apiVersion: v1
  kind: PersistentVolumeClaim
  metadata:
    name: hyperv-csi-smoke
  spec:
    accessModes: [ReadWriteOnce]
    storageClassName: {{ .Values.storageClass.name }}
    resources:
      requests:
        storage: 1Gi
  YAML

  kubectl get pvc hyperv-csi-smoke -w

Bound means the agent created a VHDX under its configured CsvVolumesRoot; the
file is named after the PVC's volume handle. If it stays Pending, the reason is
in the provisioner's events and the driver's logs:

  kubectl describe pvc hyperv-csi-smoke
  kubectl logs -n {{ .Release.Namespace }} deploy/{{ include "hyperv-csi.fullname" . }}-controller -c hyperv-csi-driver
  kubectl logs -n {{ .Release.Namespace }} deploy/{{ include "hyperv-csi.fullname" . }}-controller -c csi-provisioner

A TLS error in the driver's logs with nothing on the agent side usually means
the client certificate's fingerprint isn't in the agent's config — the agent
rejects unrecognized callers during the handshake and logs the fingerprint it
was shown.

Note: the StorageClass reclaims with Retain, so deleting the PVC leaves the PV
and the VHDX behind, to be removed by hand. DeleteVolume is implemented — set
storageClass.reclaimPolicy=Delete once you have seen it succeed against your
own hosts.

{{- if .Values.controller.nodeFencing.enabled }}

Node fencing is enabled. When a node goes unreachable and the Hyper-V cluster
confirms its VM is not running anywhere, the driver applies
node.kubernetes.io/out-of-service to that Node, which is what lets Kubernetes
force-delete the stranded pods and detach their volumes.

The one thing to know operationally: the driver applies that taint and never
removes it. Clearing it is a manual step during node recovery —

  kubectl taint nodes <node> node.kubernetes.io/out-of-service-

Until you run it, a node that has recovered and is otherwise healthy stays
out-of-service and will not run pods. This is deliberate: removing the taint
while volumes are still detaching would undo the thing it was applied for.

  kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
{{- end }}
{{- if .Values.agent.allowInsecure }}

WARNING: agent.allowInsecure is set. The connection to the agent has no TLS and
no client certificate, which is the only thing that stops anything able to route
to the agent from creating and deleting volumes. Development only.
